# CLAUDE.md

Guidance for AI coding assistants and developers working in this repository.

## Product

**LexiRAG** — "Understand law. Across languages." A multilingual legal document intelligence platform for Indian legal work. Users organise PDFs into **workspaces** and ask questions where the **document language, question language and answer language are independent**. Languages: English (`en`), Hindi (`hi`), Bengali (`bn`), Marathi (`mr`), Punjabi in Gurmukhi (`pa`), French (`fr`).

**Current phase: 2 (RAG engine).** These work end to end:
- Ingestion: PyMuPDF with optional Tesseract OCR → language detection → legal-aware chunking → BGE-M3 → pgvector.
- Hybrid retrieval: dense + BM25 → RRF → bge-reranker-v2-m3.
- Grounded answers via Ollama, Anthropic or Gemini, with server-validated citations.
- Chat UI with conversations, citation → PDF page navigation, and an evaluation harness.

## Architecture

```
Browser (React SPA, :5173) ──HTTP/JSON──▶ FastAPI (:8000, /api/v1) ──SQLAlchemy──▶ PostgreSQL 16 + pgvector (:5433)
                                               ├─▶ Local file storage (STORAGE_DIR/documents/<workspace_id>/<uuid>.pdf)
                                               ├─▶ In-process models: BGE-M3, bge-reranker-v2-m3 (lazy singletons)
                                               ├─▶ LLM provider (Ollama HTTP / Anthropic SDK / Gemini HTTP)
                                               └─▶ single-worker processing queue (thread) for ingestion
```

- A modular monolith in one backend process. Ingestion runs on one in-process worker thread (`app/services/processing.py`). Don't add Celery or Redis without a measured need.
- `app/rag/` holds the RAG components and never imports the API layer. The pure components (extraction, language, chunking, bm25, fusion, answering) are unit-testable without the database or models.
- Layering: `api/v1` (HTTP) → `services` (transactions, file I/O, orchestration) → `rag` / `models`.
- A single `.env` at the repo root is read by the backend, Vite (`envDir: ".."`), Docker Compose and the scripts.

## Testing

```bash
cd backend && <venv-python> -m pytest                 # needs the docker db; uses <POSTGRES_DB>_test
cd backend && <venv-python> -m pytest -m "not models" # skip real-model tests
cd frontend && npm test && npm run typecheck && npm run build
```

- Tests set `AUTO_PROCESS_UPLOADS=false`, `RERANKER_ENABLED=false`, small chunk sizes and no LLM. Use the `fake_models`, `fake_llm` and `sync_queue` fixtures.
- If a migration changes while `lexirag_test` exists, drop that database; it is recreated automatically.
- Run the relevant suites after every change, and never report tests you did not run.

## Database and migrations

- Every schema change needs a new Alembic migration. Review autogenerated files, then run `alembic upgrade head` and `alembic check`. Never use `create_all`, and never edit migrations that have been released.
- Constraint names follow `app/database/base.py`. Wrap explicit names in `op.f()` in migrations.
- Check constraints mirror `ProcessingStatus` and `MessageRole`, so change both together.
- The vector dimension is 1024 (`EMBEDDING_DIMENSION`). A different embedding model needs a migration and re-processing.

## Coding conventions

- Python 3.13 with typed SQLAlchemy 2.0 and Pydantic v2. Routes are sync `def`.
- Raise `AppError` subclasses (API) or `app.rag.errors` types (`ExtractionError`, `ModelUnavailableError`, `LLMNotConfiguredError`, `LLMProviderError`, `OcrUnavailableError`). `core/errors.py` maps them to the `{"error": {...}}` envelope. Messages must be actionable and must not contain paths or secrets.
- Models load lazily through `get_embedding_model()` and `get_reranker()`. Never load them per request, and never download implicitly.
- Files: names are generated server-side, paths go through `LocalStorage.resolve()`, files are written as `.part` and then renamed, and they are deleted only after the DB commit.
- Frontend: TS strict, server state in `hooks/queries.ts` (statuses are polled while in progress), all HTTP through `services/api.ts`, and `types/api.ts` kept in sync with `backend/app/schemas`.

## Brand and design rules

- Monochrome legal-tech look: Newsreader for display, Inter for the UI, subtle borders and restrained shadows.
- Indic text renders through the bundled Noto faces (`src/fonts.css`), placed first in both font stacks and scoped by `unicode-range`. Do not put a broad Latin font before them.
- Prohibited: vendor "Powered by" credits, OpenAI or Anthropic branding, robot avatars, neon, glows and heavy gradients.

## Important implementation rules

1. **Never fake AI.** Show no answers, statuses, scores or language results that the backend did not produce. Statuses run `uploaded → queued → extracting → chunking → embedding → indexing → completed | failed`.
2. **Citations are validated on the server.**
   - Only source ids that were given to the model can become citations.
   - Names, pages and sections come from the database (`page_spans`/`section_spans`), never from model text.
   - A quote that can't be verified falls back to the stored passage with `quote_verified=false`.
   - An answer with no valid citation becomes `evidence_sufficient=false`.
3. **Retrieved text is untrusted.** It is fenced in `<source>` tags (tags inside it are neutralised), and the system prompt forbids following instructions from sources.
4. **Highlighting** (`frontend/src/lib/highlight.ts`) marks only contiguous matches at character level, inside spans that pdf.js rendered (always HTML-escaped). Never fall back to fuzzy or partial word matching that can mark unrelated text.
5. **New conversations** are created by `POST /chat/messages` only after a successful answer. Don't create empty conversations from the UI.
6. **Workspace isolation** is enforced in SQL (`document_chunks.workspace_id`), and requested document ids are checked against the workspace (404 if they don't belong).
7. The app must stay usable (upload, processing, search) **without an LLM key**. Answering then returns a clear 503.
8. Never commit `.env`, uploads, model weights or credentials. API keys go in headers, never in URLs or logs.
9. Scripts must be idempotent, equivalent across platforms, compatible with Windows PowerShell 5.1 (ASCII only, no `&&`) and bash 3.2, and saved with **LF** line endings for `.sh` files (editors here write CRLF; convert them).
10. Never download large models automatically. Setup downloads them only with `-DownloadModels` / `--download-models`.
11. Ask before destructive operations.
12. Fixtures and evaluation data are **synthetic** unless an item says `validated: true`. Never present synthetic results as real-world quality.

## Defaults (tune only with evaluation evidence)

These are the starting values:
- Chunks: 700 / 120 / 120 tokens.
- Candidates: dense 30, BM25 30, RRF k = 60.
- Reranking: 16 candidates reranked down to 6.
- Models: Gemini `gemini-3.5-flash`, Anthropic `claude-opus-5-5` (effort `medium`).

## Phase 3 candidates

- Detection of legacy-font Hindi PDFs (Kruti Dev), with OCR fallback.
- A durable job queue, authentication, streaming answers.
